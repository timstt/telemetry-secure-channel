## Жадібний планувальник (`src/Telemetry.System/Scheduler.cs`)

### Постановка

Є готові пакети k = 1..n: цінність `V_k` (сума `v_i` кадрів) і розмір `b_k = 8·(75 + payload)` біт,
отже час передавання `t_k = b_k / bandwidth`. Канал (`channel.py`) іде по пакетах у заданому порядку:
якщо `clock + t_k > budget`, пакет **пропускається**, а наступні, менші, ще можуть пройти.
Потрібен порядок, що максимізує сумарну цінність переданих пакетів (без урахування втрат).

Це **рюкзак 0/1**: місткість — бюджет часу, вага — `t_k`, цінність — `V_k`. Порядок відправлення
визначає, у якій послідовності канал «пробує» предмети: «бери, якщо влазить, інакше пропусти».

### Алгоритм

Сортування за щільністю `V_k / t_k` за спаданням; рівні — більша `V_k`, далі менший індекс.
Смуга однакова для всіх пакетів сеансу, тому `V_k / t_k ∝ V_k / b_k`. Щільності порівнюються
точно в цілих: `V_a·b_b` проти `V_b·b_a`. Складність `O(n log n)` (сортування).

Властивості: порядок детермінований, не залежить від seed каналу (втрати не враховуються взагалі)
і від порядку вхідного масиву.

### (1) Жадібний за щільністю може бути неоптимальним — контрприклад на 3 пакетах

Бюджет 50. Пакети `(V, t)`: A = (60, 10), B = (100, 20), C = (120, 30).
Щільності: A = 6, B = 5, C = 4 → порядок A, B, C.
Канал передає A (10) і B (30 разом), C вже не влазить (30 + 30 > 50). Цінність **160**.
Оптимум — B + C (час 50): **220**. Жадібний програв, бо «з'їв» бюджет дрібним щільним A, і великий C
не вліз. (Тест `Greedy_counterexample_on_three_packets`.)

### (2) «Найкращий із двох» дає ≥ ½ OPT

Варіант: `max(жадібний набір, найцінніший окремий пакет, що влазить)` — `Scheduler.BestOfTwo`.

Доведення. Нехай пакети впорядковано за щільністю, і `k` — перший пакет, що не вліз у префікс.
1. Дробовий рюкзак розв'язується жадібно оптимально: префікс `1..k−1` плюс частина `k`.
   Тому `OPT ≤ OPT_дробовий ≤ V_1 + … + V_{k−1} + V_k`.
2. `V_1 + … + V_{k−1} ≤ жадібний` (жадібний бере щонайменше цей префікс), а `V_k ≤ V_max`
   (кожен пакет окремо влазить у бюджет).
3. Отже `OPT ≤ жадібний + V_max ≤ 2·max(жадібний, V_max)`, тобто `max(...) ≥ OPT / 2`. ∎

Оцінка точна з точністю до сталої: на прикладі «маленький щільний пакет + великий цінний» чистий
жадібний може бути як завгодно гіршим (тест `Best_of_two_beats_greedy_when_one_big_packet_dominates`),
а «найкращий із двох» — ні (тест на 300 випадкових прикладах з перебором оптимуму).

### (3) Чому за майже однакових розмірів порядок зводиться до сортування за V_k

Якщо `b_k ≈ b` для всіх k, то `V_k / t_k = V_k · bandwidth / b_k ≈ (bandwidth / b) · V_k` — множник
однаковий, тож порядок за щільністю = порядок за `V_k`. У нас пакети формуються під ліміт 512 Б, тому
більшість має майже однаковий розмір, і планувальник фактично ставить найцінніші (з критичними кадрами)
першими. (Тест `Near_equal_sizes_reduce_to_sorting_by_value`.)

### Базові лінії для таблиці 4

- **FIFO** (`FifoScheduler`) — за часом створення = вимкнений планувальник.
- **Випадковий** (`RandomScheduler(seed)`) — Фішер — Єйтс із фіксованим seed.
Порівнюємо R і Q в аварійному сценарії (бюджет 16,9 с не вистачає на всі пакети), на 5 seed каналу.

## Мікрозміни (E2)

1. **Канал удвічі вужчий.** `t_k` подвоюється, у бюджет влазить удвічі менше пакетів. Порядок за
   щільністю не змінюється (множник однаковий), але конкуренція за бюджет сильніша, тому важливіше,
   щоб критичні кадри були в перших пакетах. Параметри: можна зменшити розмір пакета (менше втрата
   цінності на пропущеному пакеті), підняти поріг NO_COMPRESSION / перевірити вигідність Гаффмана;
   це гени ГА — перезапустити ГА на новій смузі.
2. **Новий тип кадру з пріоритетом вище за всі.** У рюкзаку: нова цінність `v_i` у `пріоритети_кадрів`,
   ДП і жадібний рюкзак підхоплюють її автоматично (вага не змінюється). У планувальнику: `V_k` пакетів
   з такими кадрами зростає, тож їхня щільність більша і вони йдуть першими — код планувальника не
   змінюється. Перевірити, що черга кандидатів (за цінністю) теж ставить їх у перші вікна.
