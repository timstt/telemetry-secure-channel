# CHANNEL_SPEC — Проєкт 1. Модель каналу

**Версія:** 1
**Реалізація:** видається готовим файлом `channel.py` у комплекті команди

---

## 0. Чому канал видається готовим кодом

Модель каналу не належить до тем дисципліни. Її самостійна реалізація не додає нічого до вивчення алгоритмів, зате створює розбіжності: дві команди, що реалізували «втрати пачками з середньою довжиною 3», легко отримають різні частки втрат, а отже різні `R` і різні `Q`. Порівнювати такі результати неможливо.

Тому `channel.py` видається готовим і **змінювати його не можна**. Команда імпортує клас `Channel` і користується ним як чорною скринькою.

Цей документ описує, що саме робить видана модель, щоб результати можна було пояснити на захисті.

---

## 1. Параметри

Беруться з секції `канал` файла `team_config.json`:

| Поле | Зміст |
|---|---|
| `loss_probability` | цільова частка втрачених пакетів |
| `втрати_пачками.середня_довжина_пачки` | `B`, середня довжина серії втрат; `1` означає незалежні втрати |
| `delay_ms` | закон затримки: стала або рівномірна на відрізку |
| `bandwidth_bps` | пропускна здатність |
| `seed_моделі_каналу` | початковий стан генератора, похідний від seed команди |

Три сценарії:

| Сценарій | Втрати | `B` | Затримка, мс | Смуга, біт/с |
|---|---:|---:|---|---:|
| спокійний | 0,00 | 1 | стала 20 | 64 000 |
| робочий | 0,03 | 1 | рівномірна 20…120 | 32 000 |
| аварійний | 0,15 | 3 | рівномірна 50…500 | 12 000 |

Seed каналу відтворюваний, тому послідовність втрат однакова від запуску до запуску. Це дозволяє налагоджувати систему на повторюваних умовах і робить вимірювання `Q` відтворюваним.

## 2. Модель втрат

Двостанний ланцюг Маркова.

```
GOOD: перед обробкою поточного пакета з імовірністю p_gb система
      переходить у BAD. Пакет, на якому стався перехід, є ПЕРШИМ
      втраченим пакетом пачки. Інакше пакет доставляється.
BAD:  пакет втрачається; довжина пачки — геометрична з середнім B
```

Формулювання «пакет, на якому стався перехід, втрачається» важливе: саме воно
відповідає псевдокоду розділу 4 і саме з нього виведено формулу для `p_gb`
нижче. Якби перехід у BAD лише готував втрату наступного пакета, формула була б
іншою.

### Вибір `p_gb`

Середня довжина серії доставлених пакетів дорівнює `(1 − p_gb) / p_gb`, середня довжина пачки втрат дорівнює `B`. Частка втрачених пакетів за повний цикл:

```
loss = B / ( B + (1 − p_gb) / p_gb )
```

Звідси

```
p_gb = loss / ( loss + B × (1 − loss) )
```

Перевірка для аварійного сценарію: `p_gb = 0,15 / (0,15 + 3 × 0,85) = 0,0556`. Середня серія доставлених пакетів `(1 − 0,0556)/0,0556 = 17,0`, цикл `17 + 3 = 20`, частка втрат `3/20 = 0,15`.

Поширена помилка — брати `p_gb = loss / (B × (1 − loss))`. Вона дає завищені втрати, приблизно 0,167 замість 0,15, бо не враховує, що перехід у BAD відбувається на пакеті, який теж втрачається.

### Виміряна поведінка

10 запусків по 50 000 пакетів:

| Сценарій | Ціль | Факт | Середня пачка |
|---|---:|---:|---:|
| спокійний | 0,000 | 0,0000 ± 0,0000 | — |
| робочий | 0,030 | 0,0303 ± 0,0006 | 1,03 |
| аварійний | 0,150 | 0,1499 ± 0,0025 | 3,16 |

## 3. Час і затримка

```
transmission_time = packet_bits / bandwidth_bps
```

Час каналу накопичується для **кожного** пакета, включно з втраченими: смуга витрачається незалежно від того, чи пакет дійшов.

Затримка додається до часу прибуття доставленого пакета і на факт втрати не впливає:

```
arrival_time = clock + delay_ms / 1000
```

### Бюджет часу передавання

Крім втрат, канал має **бюджет** `transmission_budget_s`. Перед передаванням
перевіряється:

```
якщо clock + transmission_time > transmission_budget_s:
    пакет не передається зовсім
```

Це і робить канал справді вузьким. Без бюджету пропускна здатність лише
змінювала б довідковий час, а дедлайн у планувальнику був би декоративним.
З бюджетом виникає реальна конкуренція за канал:

- в аварійному сценарії бюджет менший за час, потрібний на весь сеанс, тому
  частина пакетів не передається взагалі;
- отже має значення, **що саме** передавач кладе в кожен пакет, і рюкзак із
  цінностями перестає бути навчальною вправою;
- отже має значення і **порядок** відправлення, тобто жадібний планувальник.

Пакети, що не вмістилися в бюджет, обліковуються окремо в `stats()` як
`не_вміщено_в_бюджет`, а `частка_недоставлених` враховує і втрати, і бюджет.

Дедлайнів окремих пакетів у версії 1 немає: недоставка визначається або станом
ланцюга Маркова, або вичерпанням бюджету.

## 5. Використання

```python
import json
from channel import Channel

cfg = json.load(open("team_config.json"))
sc  = cfg["канал"]["сценарії"]["аварійний"]
ch  = Channel(sc, cfg["канал"]["seed_моделі_каналу"])

for pkt in packets:
    delivered, arrival = ch.send(pkt)
    if delivered:
        receiver.accept(pkt)

print(ch.stats())
# {'надіслано': ..., 'втрачено': ..., 'не_вміщено_в_бюджет': ...,
#  'частка_втрат': ..., 'частка_недоставлених': ...,
#  'час_каналу_с': ..., 'бюджет_с': ...}
```

`stats()["час_каналу_с"]` — це час зайнятості каналу. Він **не** входить у компоненту `T` метрики `Q`: `T` вимірює час обчислень системи, а не час передавання. Обидва числа наводяться у звіті окремо.

## 6. Що з цього питається на захисті

- Чому `p_gb` не дорівнює `loss`, і як виводиться правильна формула.
- Чому втрачений пакет усе одно займає смугу.
- Як зміниться `R`, якщо застосувати дублювання критичних кадрів у сусідніх пакетах, і чому виграш більший саме за пачкових втрат.
- Чому за `B = 3` дублювання в **сусідніх** пакетах працює гірше, ніж рознесення дублів на кілька пакетів.
- Що станеться з `R`, якщо збільшити розмір пакета: менше накладних витрат на заголовки, але грубіша втрата за одного збою і швидше вичерпання бюджету.

### Про seed

Seed у `team_config.json` відкритий і призначений для налагодження. **Офіційне значення `Q` викладач рахує на прихованих seed з усередненням за п'ятьма прогонами.** Тому підбирати розклад втрат наперед, знаючи відкритий seed, безглуздо: на офіційному вимірюванні розклад буде інший. Усереднення заодно зменшує випадковість оцінки.
